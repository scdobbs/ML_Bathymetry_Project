## 2. Challenge clause (§0) — wrong or underspecified instructions, with evidence, and the executor's calls

1. **§A1 "if a frozen builder cannot be called for a single pair without editing it, write a thin wrapper".** Three wrappers, no frozen file edited: (a) `build_tiles_targets.process_pair` and `build_inputs_r06.process_pair` write under module-level roots (`FIELDS`, `r06_common.FIELDS`), re-pointed to the mode's root; (b) `C4.UNIT_OF` is extended with the pair's `leakage_unit` for pairs outside the frozen development list (the sealed pairs at Phase 4; `build_tiles_targets`, `fields_r08` and `build_features` index it); (c) `fields_r08.one_pair` renders a labelled set-B page from a prediction column, so it is given an all-NaN table and its set-B pages and metrics stay in `figures/work/`, never assembled or delivered.
2. **§A1 modes "differ only in the pair list, the guard allow-list and the output root".** The locks of §A1 are themselves phase4-mode branches (sign-off, pre-registration / artifact / script hashes, calls file, single run); every branch is listed with line references in §3 (`tables/mode_branches.md`). The allow-list is applied after the locks, so in this directive no run ever reached it (phase4 mode was exercised only through `enforce_locks`).
3. **§A1 lock 3 and §B6 are circular on the five scripts' hashes.** The pre-registration lists the scripts' sha256 and the scripts verify themselves against it; the scripts therefore embed no v2 sha256 and read the expected one from the sign-off file. The hashes in the v2 draft are those of the scripts at this commit; any later edit to a Phase 4 script needs a pre-registration revision before Phase 4.
4. **§A2 feature tolerance 1e-9.** Two log-count features differ by one float32 ulp and one anisotropy value by 7e-9; the NaN pattern is identical and everything else is at 0. The cause is the CPU generation (R04: AMD Genoa 9384X; rehearsal: AMD Rome 7742); numpy's float32 SIMD log10 is not bit-stable across them. Reported as HOLD H3 rather than as a build defect.
5. **§A4 P-V1 CPU tolerance 1e-3 in log₁₀.** The R07 predictions were made under GPU bf16 autocast; CPU float32 gives 1e-2 differences on single blocks while the tile ρ is unchanged to three decimals. HOLD H3, as the directive foresees.
6. **§A6 "each pair as its own unit".** `phase4_score.py` scores a pair table directly (role column: development / EW0207 at rehearsal; confirmatory / lockbox at Phase 4) and never calls `eval_v1_1.assert_units` (which refuses sealed ids); the per-pair ρ is `eval_v1_1.rho`. For single-pair units the interior-tile ρ equals R08b's unit value to 1e-9 on all 9 single-pair units scored on the interior view (`tables/r08b_consistency.md`).
7. **§A6 rehearsal convention.** `ab_whole_survey = yes` wherever the R08 criteria include a or b (the R08 calls have no such field); the GBT_ship and P-V1 columns of EW0207 come from the §A4 artifact predictions, the development pairs' from the held-out R08b master table (§0.3); EW0207's s_lr_W64 and the development pairs' from R08 `rows_W64.parquet`.
8. **§A6.3 random streams.** One `default_rng(20261012)` per pair for the subsets, consumed in the order B = 4, 6, 8, 12, 16; one `default_rng(20261009)` per subset for its 1,000-resample bootstrap (the B4 seed). Only 6 of 39 pairs reach 64 blocks, so the pooled coverage rests on lu00, lu05, lu08, lu13 (two pairs) and EW0207.
9. **§A6.5 and the sealed manifest rows.** The confirmatory rows carry `None` / NaN in every path, spacing and k column; `phase4_build.py` refuses such a row, so Phase 4 step 1 (acquisition repo) must fill `hr_native_res_m`, `lr_native_res_m`, `max_recoverable_k` and the harmonized paths. Stated in the v2 draft B3 step 1.
10. **sbatch `--export` splits on commas**, so the first build job received only the first pair id; the pair lists are now space-separated (`phase4_common.split_pairs`), and the build was rerun for the two remaining pairs (`47244463`). The rehearsal chain was resubmitted once after a pandas MultiIndex error in the comparison script (fixed).
