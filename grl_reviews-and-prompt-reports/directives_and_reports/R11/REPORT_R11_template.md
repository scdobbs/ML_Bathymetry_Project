## 2. Challenge clause (§0) — wrong or underspecified instructions, with evidence, and the executor's calls

1. **§A1.2 "if the code does not already do this".** It does: the frozen builder reads only `ship_products_usable` (§3.1). The directive's alternatives (the products' `available` flags, a ruling list in code) are not consulted anywhere; the rulings live in the manifest's `ship_products_usable_reason` / `ruling_source` columns. Only bookkeeping was added.
2. **§A2.2 "the path it reads".** `sealed_step1.write_run_record` writes `<acquisition repo>/reports_post_grl_review/ACQ-R06b/step1_run_phase4_<tag>.json` (tag `run` without `--run-tag`). That directory already holds a `step1_run_phase4_run.json` with status `stopped (rule C4)` from the ACQ-R06 refusal tests (a dummy sign-off and freeze record on scratch; stopped at the swath preflight); the lock therefore requires status complete, `phase4` mode and both citations, and test 27d shows it refuses that directory as it stands. The real run will overwrite that file.
3. **§A2.3 EX1202L2 in rehearsal mode.** EX1202L2__MGDS_20815 is a v2.1 development row without k (`r04_common.NOT_USED_NO_K`), not in the rehearsal admission list of R10, so `phase4_build.py` would have refused the pair list. The no-k development rows of v2.1 were added to the rehearsal admission (their only outcome is `not scorable (no k)`); phase4 admission is unchanged. `--rows` and `--out_root` (build) and `--rows` / `--acq_record` (score) are rehearsal-only and refused in phase4 mode.
4. **§A3 "from the supplement row or the acquisition run record".** The supplement row carries k and `k_sweep_status` but no per-k verdicts and no explicit source column (the source is inside `notes`); the run record's `per_pair` entry carries `per_k`, `k_source` and `values_source`. Both are read, and the row's k is checked against the record's.
5. **§B2 "SD of the valid coarsened cells".** The frozen path does not take the SD of native cells: `tile_ship_side` area-averages the LR raster onto `lr_px = max(2, round(256 × hr_res / lr_native))` cells over the window and `build_inputs` takes the SD of those (≥ 2 valid, else None). The coarsened s_lr goes through exactly that path with `lr_native' = f × lr_native`, so for the twelve 1 m pairs `lr_px = 2` (four resampled cells of about 128 m) — which is also what the sealed pairs will get at Phase 4. "Cells across" is reported as 256 × hr_res / (f × posting). For pairs whose HR spacing exceeds 1 m (AT42-06 5 m, KM0923 / EW9801 / tag_m127 / AR26 about 2 m) the 256-px window is wider than 256 m, so their cells across stay above the sealed values; the sealed pairs' HR spacing is 1.0–1.04 m.
6. **§B3 "on interior tiles at D₁".** `score_pair` was run unchanged (B4 rules, B_min = 8), so TN399__MGDS_33068 and AR26 use the fallback view as in R10b; the original row beside each pair is R10b's `per_pair_D1.csv`, and the original pooled row is recomputed on the same inputs (it equals R10b's whole-pool value +0.392 [+0.317, +0.430]).
7. **§C1 "add 'and R11' after 'R10 and R10b'".** Applied literally ("directives R10 and R10b and R11"); REPORT_R11 added to the guard-evidence list (REPORT_R10b was already there).
8. **Working tree.** As in R07–R10b: uncommitted June 2026 edits remain in `models/`, `training/`, `preprocessing/data_utils.py`, `CLAUDE.md`, `METHOD.md`; no R11 script imports those modules (the Part B driver imports `preprocessing/extract_clean_patches.py` and `colocated_utils.py`, which are committed and unchanged).
